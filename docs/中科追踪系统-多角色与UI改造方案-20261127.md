# 中科追踪系统 · 多角色权限 / 分包商隔离 / UI 改造评估

> 日期：2026-11-27
> 配套文档：`中科追踪系统-业务逻辑与财务审计-20261127.md`
> 结论前置：**UI 不换框架，改"收口 + 合并"；分包商端不塞进现有巨石，另起轻量门户。**

---

## 0. 一页纸结论

| # | 结论 | 理由 |
|---|---|---|
| 1 | **不换 UI 框架**（不上 antd/Mantine/整站重写） | 技术栈已是 2024 主流（React18+Vite5+Tailwind3.4+Radix27+shadcn），无框架混入；问题在"实现混乱"不在"引擎旧" |
| 2 | 真正该做的是**把 6 个财务巨页合并成 1 个模板** | 这 6 页 ≈15,700 行、~90% 结构重复（源码自注"完全复制自 PaymentAudit"），合并后降到 ~4,500 行 |
| 3 | 多角色要拆成**两个正交维度** | 角色决定"能进哪些页面"；伙伴绑定决定"能看到哪些行"。今天混在一起，是权限失效的根因 |
| 4 | 分包商登录**必须新建 user→partner 绑定**，现有 `partnerId` 是伪造的 | `AuthContext` 取"第一个货主"，所有外部账号看到同一家 |
| 5 | 分包商端建议**独立 Vite 入口**，不复用 158 页巨石 | 外部角色只读 5~8 个页面，塞进零测试的 17 万行代码里风险远大于收益 |
| 6 | 差异化运费必须**行级 + 字段级双过滤** | `base_amount` 存的是我司采购成本，只做行过滤仍会漏出成本价 |

## 1. 现状诊断：多角色支持到什么程度

### 1.1 角色体系

| 项 | 现状 |
|---|---|
| 来源 | 数据库枚举 `app_role`：`admin / finance / business / operator / viewer / fleet_manager / driver / partner` |
| 定义分散 | 前端 4 处重复定义（`types/permission.ts`、`contexts/AuthContext.tsx`、`types/permissions.ts`、`types/index.ts`）+ 1 处 `ROLES` 常量 |
| 新增角色 | 必须 `ALTER TYPE app_role ADD VALUE`（`RoleManagementService.createRole`），**不能只插模板表** |
| 现有各角色菜单 | admin 全量；finance 财务全量+合同；business 业务+对账；operator 几乎全业务（含 `project.view_all`，**过宽**）；partner 仅 3 个看板菜单；viewer 只读全量 |

### 1.2 权限有 **5 套并存实现**，且守卫用的是最弱的一套

| 实现 | 数据源 | 谁在用 |
|---|---|---|
| `useSimplePermissions` | **只读 `role_permission_templates`**，完全不看 `user_permissions` | **路由守卫 + 侧边栏 + 动态菜单** ← 关键 |
| `useUnifiedPermissions` | 有用户权限记录则**整体替换**角色模板 | 少量页面 |
| `useAdvancedPermissions` | `inherit_role` 为真才做并集（**唯一语义正确的实现**） | 仅权限管理页 |
| `useOptimizedPermissions` | 同上 + 回写 | 11 处 |
| DB `has_*_permission()` | 用户全局权限优先，否则角色模板 | 全部 `_1126` RPC |

**后果**：管理员在「用户权限」界面给某人加菜单，该用户**仍然进不去**（守卫只看角色模板）；反之收权也收不掉。

### 1.3 前端调用面的真实水平

| 指标 | 实测 |
|---|---|
| 前端 `.rpc()` 调用点 | 241 处 / 去重 139 个函数 |
| 库内声明函数 | 456 个 |
| 前端调用但库内无定义 | **13 个**（收款 4 + 对账 1 + 合同权限 8） |
| 库内有但前端不用 | 332 个（73%） |

### 1.4 数据隔离：RLS 名义存在，实际被 RPC 绕过

| 层 | 现状 | 有效吗 |
|---|---|---|
| 直查表 `.from()` | 750 处（占 76%） | 部分有效 |
| RLS 策略 | 核心 7 张表有；`partners` 是 `USING(true)`；`user_permissions`/`user_projects`/`role_permission_templates` **未启用** | 部分失效 |
| 视图 | 全部缺 `security_invoker` | **全绕过 RLS** |
| RPC | 170+ 个 `SECURITY DEFINER`，**0 个 `SECURITY INVOKER`**；仅 `_1126` 系列内部校验权限 | **主路径不过 RLS** |

> 一句话：**只要走 RPC（业务页面全走 RPC），RLS 就等于没开。**

## 2. 目标模型：两个正交维度

### 2.1 维度一 · 角色（能进哪些页面）

| 角色 | 定位 | 建议可见菜单 | 关键约束 |
|---|---|---|---|
| `admin` | 平台超管 | 全部 | 唯一可改权限/角色 |
| `finance` | 财务 | 财务概览、付款/开票/收款/对账、合作方余额、报表 | 不做业务录入 |
| `business` | 业务员 | 业务录入、运单维护、司机/地点、合同 | **不可见成本与利润**（见 2.3） |
| `operator` | 操作 | 业务 + 部分财务 | **收回 `project.view_all`**（当前过宽） |
| `partner_shipper` | 货主（新增） | 我的运单、我的账单、我的余额、回单提交 | 只见自己及下级 |
| `partner_carrier` | 分包商（新增） | 我的运单、我的结算单、对账确认 | 只见自己一行金额 |
| `fleet_manager` | 车队长 | 内部车队 | 现有能力保留 |
| `driver` | 司机 | 我的运单/报销/工资 | 现有能力保留 |
| `viewer` | 只读 | 看板 | **去掉 `data.all`** |

> 建议把现有 `partner` 拆成 `partner_shipper` / `partner_carrier`：两者的可见字段、可做动作完全不同（货主看应收和自己的余额；分包商看应付和自己的结算单）。若不想动枚举，用 `partner_type` 驱动分支也可，但枚举更清晰。

### 2.2 维度二 · 伙伴绑定（能看到哪些行）

```
user (profiles.id)
   │ 1..N
   ├── user_partners(user_id, partner_id, relation, is_primary)
   │        relation: 'owner'（本主体）/ 'viewer'（代管）
   └── 派生：visible_partner_ids = 本主体 + 全部下级（hierarchy_path LIKE）
```

**新建表 `user_partners`**（不要用 `profiles.partner_id` 单值，因为一人可能管多家、且货主有下级）：

```sql
CREATE TABLE public.user_partners (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES public.profiles(id) ON DELETE CASCADE,
  partner_id uuid NOT NULL REFERENCES public.partners(id) ON DELETE CASCADE,
  relation text NOT NULL DEFAULT 'owner',     -- owner / viewer
  is_primary boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (user_id, partner_id)
);
```

配套函数（仿现有 `get_current_driver_id()` 的成熟范式）：

```sql
get_current_partner_id()      -- auth.uid() → user_partners 主绑定
get_visible_partner_ids()     -- 本主体 + 全部下级（复用 hierarchy_path）
```

### 2.3 三个可见域（决定看到什么字段）

| 域 | 谁能看 | 可见字段 |
|---|---|---|
| **成本域** | admin / finance | `payable_cost`、`current_cost`、`unit_price`、`base_amount`、全部层级 `payable_amount`、利润率 |
| **经营域** | business / operator | 运单本身（司机、车牌、装卸、重量、日期），**不含任何金额** 或仅含总额 |
| **结算域（对外）** | partner_* | 只有**自己那一行**的 `payable_amount`（分包商）或最高层 `payable_amount`（货主） |

> 现在 business/operator 能看到全部金额与成本，这是**内部数据泄露风险**，也应在这次一并收口。

## 3. 分包商隔离方案（分三步落地）

### 3.1 P0 止血（1-2 天）—— 先把"串号"堵住

| 动作 | 具体 |
|---|---|
| 建 `user_partners` 表 + 绑定管理界面（挂到合作方详情页） | 一人可绑多个主体 |
| 删除 `AuthContext` 的伪造逻辑 | `AuthContext.tsx:212-218`、`:256-262` |
| 加 `REVOKE EXECUTE ON FUNCTION ... FROM anon, PUBLIC` | 运单/成本/余额类 RPC 全部收回 |
| 补 `user_permissions` / `user_projects` / `role_permission_templates` 的 RLS | 当前可被 anon key 直写 = 可自行提权 |

### 3.2 P1 业务可用（3-5 天）—— 让分包商真的只看自己

改造读类 RPC，统一在**入口处**做身份裁决（不是在前端过滤）：

```sql
-- 每个对外的读函数开头
v_role := (SELECT role FROM profiles WHERE id = auth.uid());
IF v_role IN ('admin','finance') THEN
    v_scope := NULL;                        -- 全量
ELSIF v_role LIKE 'partner%' THEN
    v_scope := get_visible_partner_ids();   -- 强制，忽略入参
ELSE
    v_scope := NULL;                        -- 内部角色
END IF;
```

需要改的函数（按优先级）：

| 函数 | 用途 | 改法 |
|---|---|---|
| `get_logistics_summary_and_records_enhanced_1201` | 运单主列表 | 加 `EXISTS (costs.partner_id = ANY(v_scope))` |
| `get_all_filtered_record_ids` | 跨页全选 | 同上（否则全选能选中别人的） |
| `get_logistics_record_by_id` | 运单详情 | 同上 + 字段裁剪 |
| `get_finance_reconciliation_by_partner_1122` | 对账明细 | **忽略入参 partner_id**，用 v_scope |
| `get_partner_balance` / `get_partner_balance_transactions` | 余额 | 去掉 `INSERT ... ON CONFLICT` 副作用 + 校验归属 |
| `get_shipper_dashboard_stats_1120` | 货主看板 | 递归 CTE 改为从 v_scope 出发 |
| `get_invoice_requests_filtered_1120` / `get_payment_requests_filtered_1120` | 单据列表 | 按 `invoicing_partner_id` / 成本行 partner 过滤 |

### 3.3 P2 兜底（3-5 天）—— 防绕过前端

| 动作 | 说明 |
|---|---|
| 所有视图加 `WITH (security_invoker = true)` | PG15+ 支持，当前是 PG17 |
| 收紧 `partners` 的 `USING(true)` | 改为 `can_view_partner(id)` |
| `can_view_partner` 改用 `user_partners` 而非 `partners.user_id` | 修掉"创建者=归属"的语义错误 |
| `logistics_records` 加 partner 分支 policy | 用 `SECURITY DEFINER` 辅助函数包一层，避免 RLS 递归（历史上踩过） |

### 3.4 差异化运费：字段级设计（关键）

现有 `logistics_partner_costs` 一行含 `base_amount`（成本）和 `payable_amount`（该层应付）。**分包商只能看后者。**

新增对外视图（只读、字段裁剪、行过滤）：

```sql
CREATE VIEW public.v_my_settlement
WITH (security_invoker = true) AS
SELECT
    lpc.id,
    lr.auto_number,
    lr.project_name,
    lr.loading_date,
    lr.loading_location,
    lr.unloading_location,
    lr.license_plate,
    lr.loading_weight,
    lr.unloading_weight,
    lr.effective_quantity,
    lpc.payable_amount,                                     -- ✅ 我的结算金额
    lpc.tax_rate,
    lpc.payment_status,
    lpc.invoice_status,
    lpc.reconciliation_status,
    -- 不暴露：lpc.base_amount / lr.payable_cost / lr.unit_price / 上游层级
    NULL::numeric AS base_amount,
    NULL::numeric AS upstream_amount
FROM public.logistics_partner_costs lpc
JOIN public.logistics_records lr ON lr.id = lpc.logistics_record_id
WHERE lpc.partner_id IN (SELECT partner_id FROM public.user_partners
                         WHERE user_id = auth.uid());
```

**展示规则（对外口径）**：

| 场景 | 分包商看到 | 不能看到 |
|---|---|---|
| 运单列表 | 运单号、线路、日期、装卸量、**我的结算金额**、我的付款状态 | 司机运费、单价、其他层金额 |
| 结算单 | 我的行合计、税点、应开票额 | 我司毛利、上游层级、base_amount |
| 对账 | 只有"我的行"，可确认/申诉 | 全链路成本结构 |
| 导出 | 同上，且导出列固定白名单 | base_amount 列 |

> **一个必须回答的业务问题**：分包商是否应该看到「我司收客户多少」？
> 若不应该（多数场景），则 `v_my_settlement` 如上即可；
> 若应该（联合投标场景），再加一列 `downstream_amount`，但要单独授权，默认关闭。

## 4. UI 评估：换不换？

### 4.1 诊断：技术栈新，实现混乱

| 反证"老旧" | 正证"混乱" |
|---|---|
| React 18.3 / Vite 5.4 / Tailwind 3.4 / Radix 27 包 / TanStack Query 5 / shadcn 全套 | 3 个财务页 8,150 行同源复制，源码自注"完全复制自…" |
| antd/MUI/element 混入 = 0 处 | 4 套分页器 / 2 套 Toast（同时挂载）/ 4 套移动布局 / 6 套下拉 / 11 套权限 hook |
| shadcn 采用率高（261 文件用 Button） | ~40% 样式绕开 design token（1,455 处 Tailwind 调色板 + 239 处 hex） |
| 路由级 code splitting 已生效（228 chunk） | 15 组 `X.tsx + 空 X/` 半途重构；`dist` 与 `vite.config` 已漂移 |
| 有公共组件层 | 公共层采用率 <10%；`zod` / `react-hook-form` / `next-themes` / `react-window` 全部空转 |
| — | `strict:false` + `supabase as any`（220 处）+ **0 测试文件** |

### 4.2 三个选项对比

| | A 收口+合并（推荐） | B 换框架 | C 整站重写 |
|---|---|---|---|
| 做什么 | 补 token、删重复组件、6 财务页合并成 1 模板、路由重构 | antd/Mantine 重做全部页面壳 | 重做信息架构 + 158 页 |
| 成本 | **65~90 人日** | 150~220 人日 | 300~450 人日 |
| 风险 | 中低（不碰 RPC/金额） | 高（98k 行 UI 重写，无类型网、无测试） | 极高（财务规则散在 UI 里，等于重新发明） |
| 收益 | 一致性 + 删 15k 行 + 暗色可用 + 首屏降 | 表格表单能力更强 | 架构重来 |
| 结论 | ✅ | ⚠️ 仅当视觉被高层否决，且只换列表+表单层 | ❌ |

**为什么 B 不划算**：要重写的核心是那 15,700 行财务列表，其价值 90% 在 RPC 调用链和状态机，与 UI 框架无关。换 antd 等于把逻辑抄一遍到新组件上，风险翻倍、收益仅视觉。且项目已经因"多套并存"而混乱，用制造混乱的方式解决混乱不成立。

### 4.3 推荐路线

**P0 地基（10-14 人日）**
- 删 14 个空目录 + `DataImport_backup` + `UserManagement.tsx_bak` + 3 个 0 引用组件
- 补 design token（success/warning/info + chart 色板 + 暗色变量）
- 接 `ThemeProvider`（next-themes 已装，只差接线）
- Toast 只留 sonner（`use-toast` 转适配层，182 个文件不用改）
- `ConfirmDialog` 包 `confirmAsync()`，替换 37 处 `window.confirm`
- 路由：`AppLayout` 提到父路由（消除 56 处重复挂载）；142 条路由拆到 `router/`
- ESLint 加行数上限（>600 warn / >900 error）+ 禁 `*_backup*`

**P1 财务模板化（25-35 人日）—— 价值中心**
- 以 `PaymentAudit`（2,584 行）为原型抽 `<ApprovalListPage />`
- `InvoiceAudit` / `PaymentInvoice` / `InvoiceRequestManagement` / `PaymentRequestsList` / `InvoiceRequest` 改为配置
- 产出：6 页 15,700 行 → ~4,500 行
- 灰度：新路径 + 动态菜单白名单 + `?legacy=1` 回旧版；回滚三档（收菜单 0 分钟 / 改路由 1 行 / revert PR）

**P2 全面收口（30-45 人日）**
- PC 基础数据页统一 FilterBar + 三态组件；合并 `Locations`/`EnhancedLocations`
- 内部车队 16 页抽模板；`FleetManagerConfig`(1,511) 拆 4 页
- 11 个权限 hook 收敛为 1 个 `useAuth().can()`（旧 hook 留 alias）
- 移动端 4 套布局收敛 2 套；补 PWA（manifest + 离线壳）
- 性能：recharts（562KB）改按需加载；`QueryClient` 配 staleTime

### 4.4 分包商端：建议独立入口

| 方案 | 评估 |
|---|---|
| 塞进现有 158 页体系 | 需在 6 个巨页里加"外部角色分支"，每个分支都要避开成本字段；零测试下改错即泄露 |
| **独立 Vite 入口 `partner.html`（推荐）** | 5~8 个页面（我的运单 / 结算单 / 对账确认 / 回单 / 余额），只调 3~4 个只读 RPC，与内部系统共享 `components/ui`，不共享业务逻辑 |

好处：外部角色拿不到内部 bundle（成本计算逻辑不进客户端）、可独立发版、可单独做移动优先设计、安全问题不外溢。

## 6. 红线清单（改造中只能搬运，不能改写）

| 类别 | 红线 |
|---|---|
| RPC | 函数名、入参对象结构、返回字段消费方式不得改；**尤其不许"顺手统一" `_1120/_1124/_1126` 后缀** |
| 金额 | 前端 229 处 `toFixed` 原样保留，不引入 decimal.js（会改变舍入结果） |
| 路由 | 142 条 path 与 query 参数不变（微信/企微/邮件已分发链接） |
| 权限 key | `dashboard.*` / `finance.*` / `maintenance.*` / `internal.*` 不得重命名（DB 菜单表存的是同一批） |
| 批量选择 | `selection.mode === 'all_filtered'` 跨页全选状态机必须完整迁移 |
| 打印 | PDF 生成器里的 hex 色是 CMYK 近似值，**不要**改成 design token |
| 开关 | `relaxedSupabase`（220 处）改造期保留，新代码另建严格层 |
| 部署 | 两个 VPS 串行部署、无 staging；周五 16:00 后禁止发布 |

### 6.1 资金类操作边界

| 操作 | 禁止 | 允许 |
|---|---|---|
| 批量重算 | 全表无 ID 的重算、业务时段执行 | 单条重算；先跑 staging 比对；执行前留 3 份金额快照 |
| 换链路 | `batch_modify_chain_1126` 批量；对已付款/已开票运单 | 单票 + 校验 `payment_status='Unpaid'` + 改完核差异 |
| 取消/作废付款 | `void_and_delete_payment_requests_1126`（删记录即断审计链） | `void_payment_for_request_1126`（需先导出 PDF 存档）—— **但当前该函数报错，修好前不得对外承诺"可取消"** |
| 直改金额 | 直接 UPDATE `logistics_partner_costs` 任何金额列 | 只读查询；测试库用 `session_replication_role=replica` 验证影响面 |
| 开 RLS | 生产直接 `ENABLE` 而不先建策略（会造成"页面全白"） | 先建 permissive 策略 → 再 ENABLE → 再逐步收紧，三步分开上线 |
