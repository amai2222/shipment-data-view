## 1. 业务全景

### 1.1 系统定位

不是 TMS（不做调度派车），也不是 WMS，而是**「运输结算台账 + 多方分账」系统**：

```
业务员录运单 → 系统按链路算每一层的应付 → 财务对账 → 向分包商付款 / 向货主开票收款
```

### 1.2 真实业务角色（与系统角色的区别）

| 业务角色 | 在系统里的表达 | 是否有登录账号 |
|---|---|---|
| 我司（平台方） | `partners.partner_type = '本公司'`，通常不出现成本行 | 内部账号 admin/finance/business/operator |
| 货主 / 客户 | `partner_type = '货主'`，链路最上层（level 最大） | 目前**无有效账号体系** |
| 分包商 / 承运商 | `partner_type = '合作商'`，中间层 | 目前**无有效账号体系** |
| 资方 | `partner_type = '资方'` | 否 |
| 司机 / 车队 | `drivers` / `internal_drivers`（内部车队是另一套） | 有（driver / fleet_manager） |

> **关键认知**：系统今天所谓「合作方登录」是货主角色 `role='partner'`，且 `partnerId` 是前端拿「第一个货主」硬凑的，不是真实绑定。见第 8 节。

### 2.2 关键表字段速查

| 表 | 关键字段 | 说明 |
|---|---|---|
| `projects` | `effective_quantity_type` | `min_value`/`max_value`/`average`，决定用哪个重量算运费 |

| `project_partners` | `chain_id`, `partner_id`, `level`, `calculation_method`, `tax_rate`, `profit_rate`, `unit_price` | **链路内的一层**：谁、第几层、怎么算钱 |

### 2.3 必须理解的三个「两套维度」

| 维度 | 第一套 | 第二套 | 风险 |
|---|---|---|---|
| 层级 | `partners` 全局树（`hierarchy_path`，谁是谁的上级公司） | `project_partners.level`（本项目本链路第几层分账） | 两套互不校验，可以配出「树上是子公司、链路里是第 1 层」的矛盾 |
| 计费 | `partner_chains.billing_type_id`（链路级） | `logistics_records.billing_type_id`（运单级） | 运单可覆盖链路，导致同链路运单计价口径不一 |
| 状态 | `logistics_records.payment_status`（运单级） | `logistics_partner_costs.payment_status`（层级） | 双写无同步触发器，可互相矛盾 |

## 3. 多链路模型

### 3.1 什么是「链路」

一个项目可以有多条并行的分账方案。典型场景：

```
项目：云南云天化化肥运输
├─ 链路A「直客链路」  计重(1)  → [货主:云天化 L3] ← [我司 L2] ← [车队甲 L1]
├─ 链路B「转包链路」  计件(4)  → [货主:中物流 L3] ← [我司 L2] ← [车队乙 L1] ← [信息部 L0]
└─ 链路C「资方链路」  计车(2)  → [货主:某贸易 L2] ← [资方:某保理 L1]
```

- 每条链路**独立**拥有自己的 `project_partners` 分层
- 运单通过 `chain_id` 归属某一条链路，**决定它按哪套规则分账**
- 同一项目下不同链路的计费方式可以不同（计重/计车/计方/计件）

### 3.2 链路切换的代价（重要）

改运单链路 = 删除旧成本行 + 按新链路重建。当前实现有缺陷：

| 问题 | 证据（【代码】） | 后果 |
|---|---|---|
| 函数内先 `DELETE` 再 `UPDATE chain_id`（触发 AFTER 重算自动插一套）再手动 `INSERT` 一套 | `20251124_replace_all_hardcoded_permissions_1126.sql:728-806` | 无唯一约束 → **成本行翻倍，金额翻倍** |
| 该函数不支持 `fixed_price`（SELECT 未取 `unit_price`） | 同上 `:739-765` | 定价法链路换链后金额被按税点重算 |
| 手工修改过的行（`is_manually_modified=true`）不删 | `20251120_add_trigger_recalc_on_effective_quantity_change.sql:75-94` | 旧链路独有合作方的手工行永久残留 |

> **线上必须核实**：`logistics_partner_costs` 是否存在 `(logistics_record_id, partner_id, level)` 唯一索引。若无（建表语句确实没有），凡换过链路的运单金额都可能已翻倍。

### 3.3 链路相关的正确心智

- 链路不是「版本」，是**并存的多条**，靠 `is_default` 标默认
- 一条运单**只能属于一条链路**（单值 `chain_id`，不是数组）
- 「一个运单同时走两条链路」在当前模型下**不支持**，只能拆成两条运单

## 4. 多分包商模型

### 4.1 组织树的维护方式

不是应用层维护，是**数据库触发器**：

```sql
-- 20250121_add_partner_unlimited_hierarchy.sql:143-177
CREATE TRIGGER trigger_maintain_partner_hierarchy
  BEFORE INSERT OR UPDATE OF parent_partner_id ON public.partners
  → calculate_hierarchy_path() 生成 "/root_uuid/child_uuid/leaf_uuid"
  → calculate_hierarchy_depth() 计算深度
  → is_root = (parent_partner_id IS NULL)
```

- `hierarchy_path` 是**根在前**的 UUID 路径，子查询靠 `LIKE path || '%'` 找全部下级
- 最大深度保护 100 层，超了只 `RAISE WARNING` 不阻断（可能产生环）
- **只有 `partner_type='货主'` 参与层级查询**（`get_all_subordinate_ids` 被改成只处理货主），分包商（`合作商`）**不在层级体系内** —— 这是做「分包商登录」时的硬缺口

### 4.2 「不同分包商看到不同运费」为什么天然可行

因为金额不是存在运单上的，是**按层存在 `logistics_partner_costs` 里的**：

```
运单 V001  payable_cost = 10,000（司机成本）
├─ L1 车队甲  tax 3%  →  payable_amount = 10,309.28   ← 车队甲登录只应看到这个数
├─ L2 我司    tax 6%  →  payable_amount = 10,638.30   ← 内部可见
└─ L3 货主    tax 9%  →  payable_amount = 10,989.01   ← 货主登录只应看到这个数
```

**结论：数据模型已经就绪，缺的只是「把行按 partner 过滤」这一层。**
但要注意：`base_amount` 字段存的是 `payable_cost`（成本价），**所有层级都能看到同一个 base** —— 分包商若能看到 `base_amount`，就等于看到了我司的采购成本。所以过滤必须是**行级 + 字段级**双过滤。

### 4.4 多层分包的表达边界（2026-11-27 澄清）

**支持的（不用改代码）**

| 能力 | 依据 |
|---|---|
| 层级数**无上限**，可 L1→L6 任意多层 | `project_partners.level` 只有 `integer`，无 CHECK 上限 |
| **每层价格可以不同**，三种算法可混用（税费/利润/定价） | 每层一行 `tax_rate` / `profit_rate` / `unit_price` |
| 一个项目**多条业务链**并行 | `partner_chains.project_id` 一对多，靠 `is_default` 标默认 |
| 同一项目不同运单走不同链 | `logistics_records.chain_id` 每条独立 |

**不支持的（模型缺口）**

| 缺口 | 说明 |
|---|---|
| **每层按上一层加价** | 重算函数里 `v_base_amount` 只在循环外取一次（运单 `payable_cost`），`ORDER BY level ASC` 只决定插入顺序，**金额不传递**。L3 的基数是司机成本，不是 L2 的应付 |
| 一条运单同时走多条链 | `chain_id` 是单值，不是数组 |
| **转包关系（谁分包给谁）** | `project_partners` 只有 `level`，**没有 parent**。无法区分「L2 从 L1 转包」和「L1、L2 是平行分包商」 |
| 分段运输 | A→B 走链 1、B→C 走链 2，只能拆成两条运单 |
| 层级毛利 | 只能靠 level 相邻相减推断，遇平行分包即算错 |

**两种业务语义的落地差异**

| 业务语义 | 现在能否表达 | 做法 |
|---|---|---|
| 每层**独立议价**（各家与上家单独谈定） | ✅ 可以 | 每层用 `fixed_price`，填各自单价 |
| 每层在**上层基础上加价**（A 加 3% 给 B，B 再加 5% 给 C） | ❌ 不能 | 需加 `parent_partner_id` + `pricing_mode`（见下） |
| 每层固定税率加点 | ⚠️ 仅近似 | `tax` 法，但基数是成本非上层，上游改价**不联动**，需手工重配每层 |

> 注意：`tax` 法在税率递增时（3%→6%→9%）金额看起来是层层递增的，容易被误认为级联加价。实际上三层都从同一个 `base_amount` 算，一旦上游改价，下游不会跟着变，**这是对账时最容易被质疑的点**。

**配置层还有一个隐患**：`project_partners` **没有 `(chain_id, level)` 也没有 `(chain_id, partner_id)` 唯一约束** → 可以配出同层两个合作方、或同一合作方两个层，重算时直接产生重复成本行（与 F-01 同源，且无法靠应用层拦截）。

**若要做真级联，最小改动（2 个字段）**

```sql
ALTER TABLE public.project_partners
  ADD COLUMN parent_partner_id uuid REFERENCES public.project_partners(id) ON DELETE SET NULL,
  ADD COLUMN pricing_mode text NOT NULL DEFAULT 'from_base';
  -- from_base   : 从运单成本算（现状，默认，向后兼容）
  -- from_parent : 从上家应付算（级联）
  -- fixed       : 固定单价（等价现有 fixed_price）

-- 防配重（先查线上有无重复再建，否则建不上）
CREATE UNIQUE INDEX CONCURRENTLY uk_pp_chain_level
  ON public.project_partners (chain_id, level);
```

重算时按 `level ASC` 维护一个 `v_prev_payable`：`pricing_mode='from_parent'` 的层用 `v_prev_payable` 替代 `v_base_amount`，其余不变。这样**不影响现有链路**（默认 `from_base`），新链路可按需开启级联。

### 4.5 各层价格到底从哪里来（配置链路实测）

**结论：纯人工逐层录入，系统不推导、不继承、不联动。**

配置入口是 `Projects.tsx` 的「新增/编辑项目」弹窗，链路编辑器里每加一个合作方，出现 4 个输入：

| 输入项 | 来源 | 默认值 | 是否联动 |
|---|---|---|---|
| 合作方 | `PartnerSelector` 选 `partners` 表 | 空 | 只回传 `partner_id` 和 name |
| 级别 `level` | **手填数字** | `chain.partners.length + 1`（`Projects.tsx:559`） | 无 |
| 计算方式 | 手选 `tax` / `profit` / `fixed_price` | `tax` | 无 |
| 计算值 | 手填，**选合作方后自动带出主数据税率** | 新增行时占位 `0.03`（`Projects.tsx:559`） | 选合作方时覆盖为 `partners.tax_rate`（`Projects.tsx:585-587`） |

**这个模型是自洽的，必须先理解它，再谈改不改：**

```
层号越大 → 越靠近货主 → 税点越高 → 金额越高
每层金额 = 司机运费 / (1 - 该层税点)
税点是「相对司机成本的累计综合税点」，不是「本层加价率」
```

实证（截图配置，司机运费按 10,000 计）：

| 层 | 合作方 | 税点 | 该层金额 | 与下层差额 |
|---|---|---|---|---|
| 1 | 山西成丰 | 6.00% | 10,638.30 | 638.30（对司机成本的加价） |
| 2 | 数创 | 6.10% | 10,649.63 | 11.33（数创留存） |
| 3 | 盛丰物流 | 6.50% | 10,695.19 | 45.56（盛丰留存） |

**关键推论**：因为 `1/(1-t)` 在 `t<1` 时单调递增，只要税点按层号递增，金额必然递增，**数学上不会倒挂**。所以不需要 `parent_partner_id`，也不需要级联算法——之前设想的「加 2 个字段做级联」在这个模型下是多余的。

三个实测结论：

1. **税点变更的正确做法是「新建链路」，不是「改原链路」——这是业务规则，不是缺陷**
   业务口径（2026-11-27 用户明确）：**税率变了就重建一条链路给新运单用，已发生的运单永远按原链路计费。**
   所以「改主数据不回溯已配置链路」是**对的**：`partners.tax_rate` 改了，已存在的 `project_partners.tax_rate` 保持不动，历史链条的计价口径被冻结。
   这也解释了多链路的第二重含义——它不只是「不同客户/不同承运方案」，还是**同一方案的历史版本容器**（旧链 + 新链并存）。

   **但系统留了一条会破坏这条规则的路径**（P1 级风险）：
   在「编辑项目」弹窗里直接改已有链路的税点并保存，`update_project_chains_incremental` 会先 `DELETE FROM project_partners WHERE chain_id = ...`（`20251120_fix_update_project_chains_add_unit_price.sql:127-128`），**DELETE 会触发 `auto_recalc_on_project_partner_change_1120`（`:418-419`）→ `recalculate_costs_for_chain_safe_1120`**，把该链路下的运单金额按新税点重算。

   保护边界（`20251120_update_all_recalc_functions_to_1120_with_fixed_price.sql:221-222`）：

   ```sql
   v_record_status.payment_status != 'Unpaid'
   OR (v_record_status.invoice_status IS NOT NULL AND v_record_status.invoice_status != 'Uninvoiced')
   → 命中则跳过重算
   ```

   | 运单状态 | 改原链路税点后 | 是否符合业务规则 |
   |---|---|---|
   | 已付款 / 已开票 | 跳过，成本行保留原样 | ✅ 正确 |
   | 已跑完但未结算 | **金额被按新税点重算** | ❌ 违反「已发生按原链路」 |
   | 未发生 | 按新税点重算 | ✅ 正确 |

   → **实操风险**：月末对账前在项目里改一次税率，当月所有「已跑完还没结算」的运单金额全部漂移。财务看到的数和司机/分包商手里的单子对不上，且无法追溯是哪次改动导致的（无配置变更审计表）。

   **建议**：链路一旦被运单引用就应锁定配置，改动只能「复制为新链路」（版本化）。这也正好复用现有多链路能力，不需要新模型。

2. **层级关系靠数组顺序 + 手填数字双重表达，两者会打架**
   - 默认 `level = 数组长度+1`：删掉中间一层后再添加，会生成重复 level
   - `level` 可任意手改，改成与已有层相同不会报错（表上无 `(chain_id, level)` 唯一约束）
   - 重算函数按 `ORDER BY level ASC` 执行，但展示组件 `PartnerChainDisplay` 用的是**数组原序**，没有按 level 排序 → **界面上看到的链路顺序 ≠ 实际分账顺序**

3. **税点这种表达方式不直观，容易配出「有层但没钱赚」的链路**
   上例里数创税点只比成丰高 0.1 个点，实际只赚 11.33 元；若业务上应赚 100 元，税点需填到约 6.88%（`1 - 10000/10738.30`）。**配置的人看到 6.0% / 6.1% 会以为差很多，实际差额被分母放大的效应吃掉了。** 这是纯业务认知问题，系统不提示。

**因此要修正两个判断**：
- 系统不是「想做级联但没做成」，而是**设计假设就是「税点是合作方的主数据属性，价格由税点推出」**
- 之前提的「主数据白维护」是错的——会带出，真正的坑是「改了不回溯」

真正该补的是：**改主数据时的批量刷新提示 + 层级唯一性 + 金额差额展示（让人看见每层到底赚多少）**，都不动财务公式。

### 4.6 链路的四重业务用途与「单件/整单加价」的口径

**链路不是一个"分账方案"就完了，它同时承担四种业务区分（2026-11-27 用户明确）：**

| # | 用途 | 数据上怎么体现 | 现状 |
|---|---|---|---|
| 1 | **不同点位/线路** | 靠 `chain_name` 写（如"XX 线"），运单靠人选 | ⚠️ 链路**没有点位字段**，选错无提示；同一项目多装/卸点组合只能靠命名约定 |
| 2 | 不同客户 / 承运方案 | 每链独立的 `project_partners` 分层 | ✅ 完整支持 |
| 3 | **计价方式差异**（税点 / 固定单价 / 单件加价 / 整单加价） | `calculation_method` + `billing_type_id` | ⚠️ 单件/整单加价靠隐式条件区分，见下 |
| 4 | 税率变更的**历史版本** | 新链接新单，旧链留旧单 | ✅ 天然支持（重算按 `chain_id` 精确作用） |

**计费严格按运单自身链路执行——这点已实现且正确：**

```sql
-- 重算入口，参数就是 chain_id
recalculate_costs_for_chain_safe_1120(p_project_id, p_chain_id, p_skip_paid)
-- 内部取该链路的 project_partners
WHERE pp.chain_id = v_chain_id ORDER BY pp.level ASC
```

- 运单 `chain_id` 决定取哪套分层规则 → 一条链只影响挂它的运单
- 换链路必须走 `modify_logistics_record_chain_with_recalc`（会重算），不会串链
- **但 `logistics_records.chain_id` 建表时允许 NULL**（`20250116_update_database_schema_comprehensive.sql:203`）。空链运单既不产生成本行、也永远不被任何重算函数命中（`WHERE chain_id = p_chain_id` 不匹配 NULL）→ 这类运单等于"游离单"，需确认前端是否强制必填

**「单件加价」与「整单加价」的实现缺陷（P1）**

业务上两种加价都要支持：按吨/件/车加（单件）和整票加固定金额（整单）。代码里 `profit` 法用**「有没有装货重量」**来隐式区分（`20251120_update_all_recalc_functions_to_1120_with_fixed_price.sql:123-129`）：

```sql
ELSIF calculation_method = 'profit' THEN
    IF v_loading_weight IS NOT NULL AND v_loading_weight > 0 THEN
        v_payable_amount := v_base_amount + (profit_rate * v_loading_weight);  -- 单件加价
    ELSE
        v_payable_amount := v_base_amount + profit_rate;                        -- 整单加价
    END IF;
```

问题有三层：

| 问题 | 后果 |
|---|---|
| **判据是「运单有没有重量」，不是业务意图** | 运单重量是必录字段 → 想整单加 100 元/票，实际算成 100 元/吨 × 30 吨 = **加 3,000 元，放大 30 倍** |
| 加价基数固定用 `loading_weight`（装货量） | 项目配置取卸货量或取小时，加价仍按装货量算，与 `effective_quantity` 口径不一致 |
| 计车链路（一车一票）也走乘法 | 计车本质是整单，只要有重量就被放大 |

**建议改法（不动表结构）**：按链路的 `billing_type_id` 决定语义，而不是看重量是否为空——

```sql
ELSIF calculation_method = 'profit' THEN
    IF v_billing_type_id = 2 THEN          -- 计车 = 一票一单 → 整单加价
        v_payable_amount := v_base_amount + profit_rate;
    ELSE                                    -- 计重/方/件 → 按有效数量加价
        v_payable_amount := v_base_amount + profit_rate * v_effective_quantity;
    END IF;
```

这样「整单加价」有了明确载体（选计车链路），「单件加价」按有效数量算，与运费主链同一个量，不再受"有没有填重量"影响。需要同步改 `calculate_partner_costs`、`bulk_calculate_partner_costs`、`batch_recalculate_*` 共 8 处实现（本就该单点化）。

### 4.7 base_amount 的注释与实现不符——以实现为准，全层不级联

**结论（2026-11-27 业务确认）：所有层级都不级联，利润也基于司机运费。现有实现正确，需要修正的是注释。**

数据库注释写的是「上一级应付金额」（`20251107_add_comments_core_tables.sql:105`），与实现不一致：

```sql
COMMENT ON COLUMN logistics_partner_costs.base_amount
  IS '基础金额（上一级的应付金额，元，2位小数）';        -- ❌ 与实现不符

-- 所有实现版本实际取的都是运单的司机运费
SELECT payable_cost, ... INTO v_base_amount, ...
FROM logistics_records WHERE id = v_record_id;            -- ✅ 全层同一个基数
```

逐版核对 `20250122:47,284`、`20251028:301`、`20251120:69,250` 全部一致；全仓 grep 级联逻辑 = 0 处。**实现是统一的、正确的，注释是历史残留。**

**最终计价口径（三种方法都基于同一个 base = 运单 `payable_cost` = 司机运费）：**

| 方法 | 公式 | 语义 |
|---|---|---|
| `tax` 税点 | `司机运费 ÷ (1 − 该层税点)` | 各层按自己的税点做含税还原 |
| `profit` 利润 | `司机运费 + 利润单价 × 有效数量` | 在司机运费上按量加固定金额 |
| `fixed_price` 定价 | `有效数量 × 链路单价` | 绝对定价，与司机运费无关 |

实证（司机运费 10,000，税点 6% / 6.1% / 6.5%）：

| 层 | 合作方 | 税点 | 该层金额 | 与下层差额 |
|---|---|---|---|---|
| 1 | 山西成丰 | 6.00% | 10,638.30 | 638.30 |
| 2 | 数创 | 6.10% | 10,649.63 | 11.33 |
| 3 | 盛丰物流 | 6.50% | 10,695.19 | 45.56 |

**这不是 bug，是设计**：税点层承担的是「开票/走账口径差异」，赚的是税差；要赚利润请用 `profit` 法（填每吨加价），不能指望 0.1 个点的税差。

**唯一要处理的**：把注释改成实际语义，否则后续维护者（包括本次审计）都会按「上一级」误读。建议：

```sql
COMMENT ON COLUMN logistics_partner_costs.base_amount
  IS '基础金额（= 运单司机运费 logistics_records.payable_cost，全层同一基数，不级联）';
COMMENT ON COLUMN logistics_partner_costs.level
  IS '合作方级别（1级、2级、3级，数字越大越靠近货主，金额越高）';
```

### 4.8 角色可见性铁律与「中科」主体的缺口

**可见性铁律（2026-11-27 明确）：外部角色一律只看自己，不做上下级穿透。**

| 角色 | 能看到 | 不能看到 |
|---|---|---|
| 分包商（合作商） | 自己在各链路里的那一行金额、对应运单、自己的收付状态 | 司机运费、其他层金额、上级利润、同层其他家 |
| 货主 | 自己在最高层的那一行金额、对应运单、自己的余额 | 下方各层价格、中科毛利、其他货主的单 |

即 `get_visible_partner_ids()` **必须严格返回本主体一个**，任何"货主看全部下级"的递归都不符合口径（已按此修正 `20261127_02_user_partners.sql`）。

**「中科」不是一个层级，是链路的归属方。**

资金流是反向的，这点最容易画错：

```
货主 → 中科 → L2 数创 → L1 成丰 → 司机
6621.50  6498.50   6397.87   6014
```

| 主体 | 钱的方向 | 在系统里怎么表达 |
|---|---|---|
| 货主（最高层 level=MAX） | 付给中科 | `logistics_partner_costs` 一行，`payable_amount` 语义实为**应收** |
| 中科 | 收上、付下 | **不产生成本行**；毛利 = 最高层金额 − 下一层金额 |
| 中间层 / L1 | 收上、付下 | 各自一行 `payable_amount`（应付） |
| 司机 | 最终收款方 | 运单 `payable_cost`（全链基数） |

**现在的缺口**：`partner_chains` 只有名称和计费类型，**没有归属方字段**，所以：

1. 链路图上画不出「中科」这个节点，配置的人容易把"货主那格"理解成"货主自己的价"，而不是"货主付给中科的钱"
2. 财务报表里中科的毛利只能靠「最高层 − 下一层」倒推，没有主体承载，无法按中科维度汇总
3. `partners.partner_type = '本公司'` 这个枚举**早已预留**（`20250122_add_partner_type_values.sql:24-35`），`PartnerSelector` 也有「本公司」标签页，但链路配置里实际没人用

**建议（1 个字段，零财务风险）**：

```sql
ALTER TABLE public.partner_chains
  ADD COLUMN owner_partner_id uuid REFERENCES public.partners(id);
-- 存量回填为中科那一条 partners 记录；新建链路默认取它
```

有了 `owner_partner_id` 就能：
- 链路图上画出中科节点（归属方）
- 报表直接 `GROUP BY owner_partner_id` 出中科维度的收入/成本/毛利
- 不需要新增成本行，不动任何计价公式

**前置确认**：`partners` 里是否已有一条 `partner_type='本公司'` 的记录。

```sql
SELECT id, name, partner_type FROM public.partners WHERE partner_type = '本公司';
```

没有就得先在「合作方管理 → 本公司」建一条（这是主数据，属于你在页面上主动操作的范围，我不会代建）。

## 5. 计费与运费计算（核心公式）

### 5.1 计费类型

| `billing_type_id` | 名称 | 有效数量取值 |
|---|---|---|
| 1 | 计重（吨） | 按项目配置：装货 / 卸货 / 取小 |
| 2 | 计车 | **固定 1** |
| 3 | 计方 | 【代码缺陷】实际仍返回吨数，未读方数 |
| 4 | 计件 | 【代码缺陷】同上 |

> 【代码】`20251120_fix_effective_quantity_by_billing_type.sql:51-54` 只特判了 `= 2`，3/4 落回重量分支。计方/计件项目的运费实际是「吨数 × 单价」。

### 5.2 运费主链（运单侧）

```
effective_quantity = f(装货量, 卸货量, 项目配置, 计费类型)

current_cost（基础运费）
   auto 模式:   ROUND(unit_price × effective_quantity, 2)
   manual 模式: 用户手填，反推 unit_price = ROUND(current_cost / effective_quantity, 2)

payable_cost（司机应收合计）= COALESCE(current_cost,0) + COALESCE(extra_cost,0)
```

### 5.3 分账公式（每个层级）

`base_amount` **统一等于运单的 `payable_cost`，不逐层级联**（所有层级共享同一基数）：

| `calculation_method` | 公式 | 适用 |
|---|---|---|
| `tax`（默认） | `base_amount / (1 - tax_rate)` | 含税加点，最常见 |
| `profit` | `base_amount + profit_rate × loading_weight` | 按吨加利润 |
| `fixed_price` | `effective_quantity × unit_price`（**不用 base**） | 直接定价 |

四舍五入：全部 `ROUND(,2)`，numeric 半离零（不是银行家舍入）。

### 5.4 举一个完整例子

```
运单：装 32.5 吨 / 卸 32.3 吨，项目配置取小 → effective_quantity = 32.3
单价 180 元/吨 → current_cost = 5,814.00
杂费 200       → payable_cost = 6,014.00

链路配置：
  L1 车队甲  tax 3%          → 6,014 / 0.97 = 6,200.00
  L2 我司    tax 6%          → 6,014 / 0.94 = 6,397.87
  L3 货主    fixed_price 210 → 32.3 × 210 = 6,783.00（应收，开票额）
```

> 注意 L2「我司」也有一行成本 —— 这是「我司自己也算一层」的设计，导致内部利润要靠 L2/L3 差额体现，账上却平级。

| F-15 | 同一公式有 8 处独立实现，其中 2 处公式不一致（利润法用 `loading_weight` vs `effective_weight`；一处无 `tax_rate=1` 保护会除零） |
| F-16 | `calculate_partner_costs` / `bulk_calculate_partner_costs` 等函数**线上存在但仓库无定义**（黑盒） |
| F-17 | 重算函数无幂等保证（无唯一键、无事务内去重） |
| F-18 | 触发器在 AFTER 阶段修改 `NEW`（无效代码），但同函数又用该值算金额 |
| F-19 | 重算守卫条件 `invoice_status != 'Uninvoiced'` 会让回滚失败的运单**永久无法重算** |
| F-20 | 状态值大小写混用（前端 `'approved'` 33 处 vs `'Approved'` 79 处），历史上 3 个互斥 CHECK |

### 7.4 修复顺序建议

第1步（不改代码，只查）：线上核实第 9 节 6 项 → 确认 F-01/F-03/F-05 真实影响面

## 8. 术语表（避免沟通错位）

| 词 | 在本系统里的确切含义 |
|---|---|
| 链路 / chain | `partner_chains` 一行 = 一个项目下的一套分账方案 |
| 层级 / level | `project_partners.level`，链路内第几层分账，**不是**组织树深度 |
| 合作方 / partner | `partners` 表一行，含货主/合作商/资方/本公司四种类型 |
| 分包商 | 口语，对应 `partner_type='合作商'` |
| 司机应收 / payable_cost | 实际是我方**应付给运力**的成本，命名反了 |
| 有效数量 | 参与计费的量，按计费类型和项目配置算出 |
| 应收 | 向 `level=MAX` 那层开票的含税金额 |
| 应付 | 向 `level<MAX` 各层付款的金额 |
| 对账 | 仅打标记（`reconciliation_status`），**不参与任何金额计算** |

## 9. 待线上核实清单（只读 SQL，执行前不得把推断当事实）

```sql
-- ① 成本行是否有唯一索引（决定 F-01 是"翻倍"还是"报错"）
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename = 'logistics_partner_costs';

-- ② payment_status 的 CHECK 是否含 'Approved'（决定付款审批是"报错"还是"漏统计"）
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
WHERE conrelid IN ('public.logistics_records'::regclass,
                   'public.logistics_partner_costs'::regclass)
  AND contype = 'c';

-- ③ logistics_records 上实际有几个触发器（决定 F-03 是否活跃）
SELECT tgname, pg_get_triggerdef(oid) FROM pg_trigger
WHERE tgrelid = 'public.logistics_records'::regclass AND NOT tgisinternal;

-- ④ 5 个收款/对账 RPC 是否真的不存在
SELECT proname FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public' AND proname IN (
  'receive_invoice_payment_1120','refund_invoice_receipt_1120',
  'reconcile_invoice_receipt_1120','get_receipt_records_1120',
  'auto_reconcile_by_waybill_1120');

-- ⑤ partner_payment_items 是否已删除（决定 F-04 严重度形态）
SELECT to_regclass('public.partner_payment_items');

-- ⑥ 已有多少运单成本行重复（只读，量化 F-01 影响面）
SELECT count(*) AS dup_groups, sum(cnt - 1) AS extra_rows FROM (
  SELECT logistics_record_id, partner_id, level, count(*) AS cnt
  FROM logistics_partner_costs
  GROUP BY 1,2,3 HAVING count(*) > 1
) t;
```

## 10. 一句话交接

> 看懂这个系统只需要记住：**运单只记成本，每一层合作方的钱都存在 `logistics_partner_costs` 里，靠 `level` 决定谁收谁付。**
> 做分包商登录只需要：**给用户绑 partner_id，把成本行按 partner 过滤，字段级藏掉 base_amount。**
> 改财务前必须先修：**换链路重复、编辑漂移、余额重复扣。** 这三条不修，任何新功能都会踩在错账上。
